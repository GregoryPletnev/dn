# LocalSend в DN — план внедрения

Оценка внедрения клиента и сервера протокола
[LocalSend](https://github.com/localsend/localsend) в DN - DataNavigator.

## 1. Цель

DN должен обмениваться файлами с устройствами LocalSend: телефонами,
другими компьютерами, в том числе с самим приложением LocalSend.
Обмен идёт по протоколу LocalSend v2 без установки сторонних программ.

Сценарии:

- Отправить выбранные файлы на устройство LocalSend.
- Принять файлы от устройства LocalSend.
- Увидеть устройства в локальной сети.
- Подтвердить приём файлов от доверенного устройства.

## 2. Что даёт протокол LocalSend

LocalSend — одноранговый протокол обнаружения и передачи. Он не даёт
доступа к файловой системе удалённого устройства.

- Обнаружение: UDP multicast `224.0.0.167:53317` и HTTP-запрос `info`.
- Передача: HTTP или HTTPS на порту `53317`.
- API: `/api/localsend/v2/register`, `/info`, `/prepare-upload`, `/upload`,
  `/cancel`, `/prepare-download`, `/download`.
- Безопасность: HTTPS с самоподписанным сертификатом, отпечаток сертификата
  в анонсе, PIN для подтверждения.
- Тела запросов и ответов: JSON. Файлы передаются бинарным потоком.

## 3. Почему текущий слой VFS не подходит напрямую

Интерфейс `TVFS` в `src/dnvfs.pas:22` описывает файловую систему:
`List`, `GetFile`, `PutFile`, `DeletePath`, `MakeDir`.

У протокола LocalSend нет листинга удалённой файловой системы. Отправитель
сам решает, что и куда положить. Получатель подтверждает приём.

Поэтому нельзя сделать `TLocalSendVFS` в виде обычной панели. Нужны две роли:

- Роль приёмника. Слушает сеть, принимает файлы, пишет их в папку приёма.
- Роль отправителя. Показывает список устройств, отправляет файлы.

Панель VFS используется только для одной задачи: показать папку приёма
и список входящих сессий.

## 4. Архитектура

### 4.1. Разделение работы

HTTP-сервер в однопоточном TUI выносится из главного цикла. Главный цикл
в `src/dn.pas` не должен блокироваться на приёме файла.

#### 4.1.1. Выбор механизма: процесс-помощник, а не поток

В проекте уже есть готовый ответ на задачу «тяжёлая работа рядом с TUI».
Плеер выносит декодер во внешний процесс (`fpFork` + `fpExecl`) и опрашивает
его неблокирующим `waitpid` из тика главного цикла (`src/dnplayer.pas:455`,
`PLAYER.md:323`). Тот же паттерн у `dnconsole.pas` и `dnsftp.pas`.

Потоки (`TThread`) в проекте не используются нигде. Выбор потока — это третий
механизм, который ломает единообразие и приносит класс проблем, которых в
проекте сейчас нет: гонки на ncurses, блокировки OpenSSL, недетерминированные
тесты.

Решение: **сервер LocalSend — отдельный процесс-помощник**. Основной вариант —
сам `dn` с флагом `dn --localsend-server`. Допустимый вариант — отдельный
бинарник `dn-localsend`.

Почему процесс, а не поток:

- ncurses не трогается из чужого контекста. Проблемы с `SCREEN` исчезают.
- `accept` и TLS-согласование живут в отдельном адресном пространстве.
  Прерывать `accept` из главного процесса не нужно.
- Падение сервера не роняет `dn`.
- Тестовый хук (`DN_LS_CMD`) встаёт на место `DN_PLAYER_CMD` без изобретений.
- Обмен через pipe и `waitpid` уже отработан в плеере.

Цена: нужен второй режим запуска `dn` или второй бинарник. Обмен усложняется:
вместо `TThreadList` — pipe с построчными событиями JSON.

Три части:

- Главный процесс. Цикл ncurses в `src/dn.pas:1939`. Рисует экран, читает
  клавиши, разбирает события из pipe.
- Процесс-помощник. Слушает TCP-порт, обрабатывает HTTP-запросы, принимает
  файлы, рассылает UDP анонсы. Обнаружение и передача — в одном процессе,
  `select` на двух сокетах.
- Обратный канал. Главный процесс шлёт решение `approve` или `reject` в pipe
  помощника.

### 4.2. Правила работы с процессом-помощником

Правило 1. Помощник не вызывает функции ncurses.

Функции `refresh`, `wrefresh`, `mvwprintw`, `getch` остаются только в главном
процессе. Помощник пишет события в pipe.

Правило 2. Обмен идёт через pipe построчными событиями JSON.

Помощник пишет по одному событию в строку. Главный процесс читает pipe
неблокирующе раз в итерацию цикла, после `getch`.

Правило 3. Главный процесс не блокируется на чтении pipe.

Чтение pipe неблокирующее, как чтение PCM в анализаторе плеера
(`src/dnplayer.pas:518`). Диск, сеть и TLS работают в помощнике и не влияют
на отзывчивость экрана.

Правило 4. Помощник живёт в своей группе процессов.

Помощник запускается через `setpgid`, как декодер плеера
(`PLAYER.md:377`). Остановка — `SIGTERM` на группу, затем `SIGKILL`.
Выход из `dn`, закрытие окна сессий и флаг остановки останавливают помощника.

### 4.3. Очередь событий

Тип события:

```pascal
type
  TLsEventKind = (leIncoming, leProgress, leDone, leError, lePeer);

  TLsEvent = record
    Kind: TLsEventKind;
    SessionId: AnsiString;
    PeerName: AnsiString;
    PeerAddr: AnsiString;
    Files: TVfsItems;
    BytesDone: Int64;
    BytesTotal: Int64;
    Err: AnsiString;
  end;
```

Очередь событий не нужна. Помощник пишет события в pipe. Формат строки —
один JSON-объект на строку. Типы событий те же:

```pascal
type
  TLsEventKind = (leIncoming, leProgress, leDone, leError, lePeer);

  TLsEvent = record
    Kind: TLsEventKind;
    SessionId: AnsiString;
    PeerName: AnsiString;
    PeerAddr: AnsiString;
    Files: TVfsItems;
    BytesDone: Int64;
    BytesTotal: Int64;
    Err: AnsiString;
  end;
```

Главный процесс вызывает `fpRead` на дескрипторе pipe, накапливает байты в
буфер и разбирает строки. Разбор строки в `TLsEvent` — чистая функция в
`src/dnlsproto.pas`, тестируется в `tests/unittests.pas`.

Обратный канал. Главный процесс пишет решение `approve` или `reject` в pipe
помощника той же построчной формой. Помощник ждёт решение на `select` с
таймаутом. Таймаут защищает от зависшего запроса.

### 4.4. Схема обмена

```
главный процесс (src/dn.pas)       помощник (dn --localsend-server)
  getch(timeout)                     select на TCP и UDP
  DrainLsPipe                        принять запрос
  прочитать строки события           записать leIncoming
  нарисовать окно                    ждать approve/reject
  записать approve в pipe            принять файлы
                                     записать leProgress
                                     записать leDone
```

### 4.5. Изменения в главном цикле

В `src/dn.pas:1939` после `getch` добавить вызов `DrainLsPipe`.

Процедура `DrainLsPipe` делает:

1. Неблокирующе читает pipe помощника.
2. Разбирает накопленные строки в события.
3. Для `leIncoming` открывает диалог подтверждения.
4. Для `leProgress` обновляет полосу прогресса.
5. Для `leDone` и `leError` показывает сообщение.

Пока открыт модальный диалог, главный цикл работает внутри `dndialog`.
Помощник продолжает принимать данные и пишет события `leProgress`.

#### 4.5.1. Хранитель экрана

Главный цикл считает `idleSecs` только когда `getch` вернул `ERR`
(`src/dn.pas:1947`). При простое запускается хранитель экрана
(`src/dn.pas:1959`).

Приём файла идёт без нажатий клавиш. Поэтому `idleSecs` растёт, и во время
передачи хранитель экрана выскочит поверх диалога приёма.

Решение: пока есть активная сессия LocalSend, сбрасывать `idleSecs` в ноль.
Активность определяется по флагу в состоянии `dnls`, который ставит
`DrainLsPipe` при событии `leIncoming` или `leProgress` и снимает при
`leDone` или `leError`.

#### 4.5.2. Таймаут главного цикла

Строка `src/dn.pas:1965` выбирает таймаут между `PlayerTickMs` и `1000` мс.

С активной сессией LocalSend нужен свой период для плавной полосы прогресса,
например 200 мс. Брать минимум из активных периодов:

```pascal
t := 1000;
if PlayerActive then t := PlayerTickMs;
if LsActive and (LsTickMs < t) then t := LsTickMs;
timeout(t);
```

Правка в двух местах: `src/dn.pas:1936` и `src/dn.pas:1965`.

### 4.6. Завершение работы

При выходе из DN помощника надо остановить.

1. Закрыть pipe помощника.
2. Послать `SIGTERM` на группу процессов помощника.
3. Вызвать `waitpid`. Если процесс жив через 300 мс, послать `SIGKILL`.
4. Забрать код выхода.

Помощник запускается через `setpgid`, как декодер плеера (`PLAYER.md:377`).
Группа процессов нужна, чтобы `SIGTERM` дошёл до дочерних процессов.

Остановка нужна в трёх местах: выход из `dn`, закрытие окна сессий,
выключение приёма в настройках.

## 5. Новые и изменённые файлы

Новые модули:

- `src/dnlsproto.pas` — модели данных протокола, разбор и сборка JSON.
  Чистая логика, без сокетов. Тестируется в `tests/unittests.pas`.
- `src/dnlshttp.pas` — HTTP-клиент и HTTP-сервер на `fphttpclient` и
  `fphttpserver`. Обёртка над TLS.
- `src/dnlsdisc.pas` — обнаружение: UDP multicast, анонс, кэш устройств.
- `src/dnls.pas` — помощник: цикл `select`, сборка сессий, запись событий
  в pipe. Главный процесс: чтение pipe, состояние сессии.
- `src/dnlsui.pas` — окно сессий, диалог подтверждения, полоса прогресса.

Изменённые модули:

- `src/dn.pas` — вызов `DrainLsPipe` в главном цикле, пункт меню
  LocalSend, запуск и остановка помощника, разбор флага
  `--localsend-server` в начале `dn.pas`.
- `src/dnconfig.pas` — настройки: имя устройства, папка приёма, порт,
  включение приёма.
- `src/dndialog.pas` — общая полоса прогресса с отменой.
- `Makefile` — новые модули в целях `$(BIN)` и `bin/unittests`. Чистые
  модули `dnlsproto` и `dnlsdisc` нужны в обеих целях
  (`Makefile:17`, `Makefile:30`).

## 6. Этапы

### Этап 1. Протокол без сети (S)

Задача: описать модели протокола и разбор JSON.

- Создать `src/dnlsproto.pas`.
- Типы: `TDeviceInfo`, `TFileMeta`, `TUploadRequest`, `TSessionStatus`.
- Функции: `ParseDeviceInfo`, `BuildDeviceInfo`, `ParseUploadRequest`,
  `BuildPrepareResponse`.
- Использовать `fpjson` и `jsonparser` из FPC.

Проверка: тесты в `tests/unittests.pas` на разбор и сборку.

### Этап 2. HTTP-клиент, отправка файла (S)

Задача: отправить один файл на устройство по адресу.

- Создать `src/dnlshttp.pas`.
- Клиент на `fphttpclient`.
- Запросы: `info`, `prepare-upload`, `upload`.
- Ручной ввод адреса `host:port`.
- Диалог подтверждения на принимающей стороне не нужен.

Проверка: фейковый пир на Python в `tests/fakelocalsend.py`. Отправка файла
на фейковый пир, сверка принятого файла.

Покрывает основной сценарий: отправить файл на телефон.

### Этап 3. Процесс-помощник и приём файлов (M)

Задача: поднять HTTP-сервер в отдельном процессе-помощнике.

- Создать `src/dnls.pas` и `src/dnlsui.pas`.
- Режим `dn --localsend-server` в начале `src/dn.pas`.
- Цикл `select` на TCP и UDP сокетах, приём файлов в папку приёма.
- Запись событий в pipe, чтение решений из pipe.
- Запуск помощника через `setpgid`, неблокирующее чтение pipe в главном
  цикле.
- Остановка помощника при выходе, при закрытии окна и при выключении приёма.
- Сброс `idleSecs` при активной сессии (пункт 4.5.1).
- Общий выбор таймаута главного цикла (пункт 4.5.2).

Проверка: тест запускает помощника, отправляет файл на DN, проверяет
появление файла в папке приёма. Тестовый хук `DN_LS_CMD` подменяет команду
запуска помощника, как `DN_PLAYER_CMD` подменяет декодер.

### Этап 4. Диалоги и прогресс (M)

Задача: показать состояние передачи.

- Общая полоса прогресса в `src/dndialog.pas` с кнопкой отмены.
- Отменяемость — новая логика. В проекте её нет ни в диалогах, ни в плеере.
  Плеерная отрисовка (`src/dnplayer.pas:601`) привязана к `TPlayerWin` и не
  переиспользуется. Это отдельный пункт ROADMAP «Progress dialogs»
  (`ROADMAP.md:15`).
- Диалог подтверждения приёма: имя устройства, список файлов, размер.
- Окно сессий в `src/dnlsui.pas`.

Проверка: TUI-тест на появление диалога и на отмену передачи.

### Этап 5. Обнаружение устройств (S-M)

Задача: найти устройства в локальной сети.

- Создать `src/dnlsdisc.pas`.
- UDP multicast `224.0.0.167:53317`.
- Анонс раз в несколько секунд, приём анонсов, кэш устройств с таймаутом.
- Ручной ввод адреса остаётся как резерв.

Проверка: два экземпляра DN видят друг друга в тестовой сети.

### Этап 6. TLS и отпечаток (M)

Задача: включить HTTPS.

- `opensslsockets` из FPC.
- Самоподписанный сертификат, хранение в `~/.config/dnfpc`.
- Отпечаток сертификата в анонсе, проверка на принимающей стороне.
- PIN для подтверждения.

Проверка: обмен между DN и настоящим приложением LocalSend.

Этап идёт после этапа 3. Ранняя отладка TLS усложняет работу.

### Этап 7. Интеграция в UI (S)

- Пункт меню LocalSend в `src/dnmenu.pas`.
- Команда `dn ls send <файл>` для отправки из командной строки.
- Настройки в `dn.ini` через `src/dnconfig.pas`.

## 7. Тесты

Тесты TUI работают в pty и проверяют экран через `pyte`. Помощник делает
тесты недетерминированными: событие приходит до или после `refresh`.

Решение: не поднимать настоящий сервер в TUI-тестах. Подавать события через
тестовый хук, как `DN_SFTP_CMD` подменяет транспорт, а `DN_PLAYER_CMD`
подменяет декодер (`PLAYER.md:352`).

- `tests/fakelocalsend.py` — фейковый пир LocalSend.
- `tests/test_localsend.py` — TUI-тесты: отправка, приём, подтверждение,
  отмена, ошибка.
- `tests/unittests.pas` — тесты разбора JSON, сборки запросов и разбора строк
  событий из pipe.

Переменная `DN_LS_ENDPOINT` задаёт адрес пира для тестов.
Переменная `DN_LS_CMD` подменяет команду запуска помощника.

## 8. Зависимости и упаковка

Новые зависимости:

- `libssl3` для `opensslsockets`. Сейчас пакет зависит только от
  `libc6`, `libncursesw6`, `libtinfo6`.
- Правка `scripts/build-deb.sh`, строка `Depends`.

Потокобезопасность OpenSSL не важна: помощник — отдельный процесс с одним
рабочим циклом. Настройка блокировок OpenSSL для многопоточного режима не
нужна.

## 9. Риски

Риск 1. Однопоточный TUI. Снимается выносом сервера в процесс-помощник.

Риск 2. TLS. Тянет OpenSSL в зависимости. Снимается этапом 6.

Риск 3. Multicast в корпоративной сети. Снимается ручным вводом адреса.

Риск 4. Нет полосы прогресса. Передача большого файла без отмены выглядит
сломанной. Снимается этапом 4.

Риск 5. Недетерминированные тесты. Снимается тестовым хуком вместо
настоящего сервера.

Риск 6. Подтверждение доверия. Нужен диалог «принять файл от X?». Без него
приём файлов от любого устройства небезопасен.

Риск 7. Хранитель экрана поверх диалога приёма. Снимается сбросом `idleSecs`
при активной сессии (пункт 4.5.1).

Риск 8. Конфликт таймаута главного цикла с плеером. Снимается выбором
минимума из активных периодов (пункт 4.5.2).

## 10. Порядок и объём

Порядок: этапы 1, 2, 3, 4, 5, 6, 7.

Этап 2 даёт рабочий сценарий отправки. Этап 3 даёт приём. Этапы 5 и 6
завершают совместимость.

Этап 3 меняет главный цикл. Правки малы: выбор таймаута, сброс `idleSecs`,
вызов чтения pipe. Механизм согласован с моделью плеера: тяжёлая работа в
отдельном процессе, опрос неблокирующе из главного цикла.

Объём: L. От 3 до 5 недель для одного разработчика.

Минимальный вариант: этапы 1, 2, 4. Около одной недели. Даёт отправку файла
на телефон без обнаружения и без TLS.

Этап внедрения зависит от пункта ROADMAP «Progress dialogs»
(`ROADMAP.md:15`). Без отменяемой полосы прогресса этап 4 не выполнить.
