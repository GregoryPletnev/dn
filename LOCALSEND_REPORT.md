Дата: 2026-10-29. Спецификация: `LOCALSEND.md`. Задача: обмен файлами с
устройствами LocalSend по протоколу v2 (клиент и сервер в DN).

### 1.3 Проверено

### 1.4 Особенности FPC, найденные при отладке

| Проявление | Причина | Решение |
| --- | --- | --- |
| `chunked` в теле PUT, пир отклоняет | `HTTPMethod` с потоком тела шлёт `Transfer-Encoding: chunked` | Установить `RequestBody := поток` и передать поток в `HTTPMethod` |
| Тело ответа не читается | FPC дописывает ответ в тот же поток после тела запроса | Отрезать тело запроса по длине в `PostJson` |
| Runtime error 232 при старте сервера | Нет поддержки потоков | Добавить `cthreads` первым в `uses` |
| `OnRequest` не принимает процедуру | Нужен метод `of object` | Класс-обёртка `TLsHttpHandler` |
| 404 на всех маршрутах | `ARequest.Command` пуст, `URI` содержит query | Использовать `ARequest.Method`; отрезать query от `URI` |

### 1.5 Правки после ревью

Ревью выявило шесть дефектов. Все исправлены.

1. **Порт помощника игнорировал аргумент.** Код всегда вызывал
   `LsHelperMain(LsDefaultPort, ...)`. Теперь порт читается из `ParamStr(2)`.
2. **Имя устройства не доходило до сервера.** `Opt.LocalSendName` не
   применялся. Добавлены `LsSetServerAlias` и `LsSetDeviceName`.
3. **Молчаливое проглатывание ошибки записи в pipe.** Теперь `Halt(1)` при
   разрыве канала.
4. **Риск выхода за границы в `dnlsproto.pas`.** `Items[IndexOfName(...)]`
   заменён на `Find(...).JSONType`.
5. **Неограниченный рост списка сессий.** Добавлена `TrimSessions` с лимитом
   64 сессии.
6. **Мёртвый параметр `Alias`.** Заглушка заменена на реальное применение.

### 1.6 Что не сделано

- Этап 4: диалог подтверждения приёма, окно сессий, отменяемая полоса
  прогресса, канал `approve`/`reject` через второй pipe.
- Этап 5: обнаружение устройств через UDP multicast.
- Этап 6: TLS, самоподписанный сертификат, отпечаток, PIN.
- Этап 7: команда `dn ls send <файл>`, раздел в `README.md`.
- Потоковая передача больших файлов: сейчас тело файла держится в памяти.
- Асинхронная отправка: `DoLocalSend` блокирует TUI на время передачи.

### 1.7 Проверка на регрессии

Падают TUI-тесты `test_menu`, `test_fileops`,
`test_archive.py::test_view_file_inside_zip`,
`test_options.py::test_confirm_delete_off`. Проверка на чистой версии `HEAD`
в этом же дереве показала те же падения. Значит, падения не связаны с работой
по LocalSend. Причина — незакоммиченные правки `src/dnscreen.pas` и `src/dn.pas`
параллельного агента (мышиные шимы, проигрыватель).

главный цикл. Сборка и модульные тесты проходят.

### Шаг 2. Устранить дефекты ревью — ВЫПОЛНЕНО

Шесть дефектов исправлены (раздел 1.5).

### Шаг 3. Этап 4: диалоги и прогресс

1. Добавить второй pipe для канала решения `approve`/`reject`.
2. Реализовать диалог подтверждения приёма: имя устройства, список файлов,

Критерий готовности: TUI-тест открывает диалог подтверждения и отменяет
передачу.

### Шаг 4. Этап 5: обнаружение устройств

Критерий готовности: два экземпляра DN видят друг друга в тестовой сети.

2. Реализовать самоподписанный сертификат в `~/.config/dnfpc`.

Критерий готовности: обмен между DN и настоящим приложением LocalSend.

### Шаг 6. Финальная проверка

3. Запустить TUI-тесты: `pytest tests/test_localsend.py`.

Критерий готовности: сборка и тесты проходят, ручной сценарий работает.

## 3. Риски

- Параллельный агент может выполнить `git stash push` по всему дереву и убрать
  правки. Следите за `git stash list` и `git status` перед сборкой.
- Правки `src/dnscreen.pas` и `src/dn.pas` параллельного агента ломают
  TUI-тесты. Падения не связаны с LocalSend, но мешают общей проверке.
- Тело файла держится в памяти при отправке и приёме. Для больших файлов нужна
  потоковая передача. Текущее ограничение приемлемо для этапа 3.
- `DoLocalSend` блокирует TUI на время отправки. Асинхронный режим — этап 4.
- Multicast в корпоративной сети часто заблокирован. Ручной ввод адреса остаётся
  резервом.
- OpenSSL требует проверки блокировок при многопоточном режиме. Помощник —
  отдельный процесс, поэтому риск ниже.
